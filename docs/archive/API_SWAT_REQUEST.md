# Запрос доработок Stuffer API (панель SWAT / StockHub)

**Статус:** для отправки разработчикам панели.
**Контекст:** SWAT — готовый продукт; автоматика (подбор курьеров, создание
пакетов, учёт) целиком на нашей стороне. От панели нужен только функционал
доступа к данным. Текущее API (`couriers`, `available_couriers`,
`add_courier`, `packages`, `labels`, `new_package`, `add_package`) покрывает
базу; ниже — какого функционала не хватает, по приоритету.

---

## 1. Создание пакета на любого доступного курьера — **критично**

Сейчас пакет можно создать только на курьера, уже назначенного нашему
аккаунту (`404 Courier not assigned`). Функционально нужно: при создании
пакета указать курьера из списка доступных — и панель сама назначит его нам
в рамках этого же действия (одно действие вместо двух: «добавить курьера» +
«создать пакет»).

Зачем: наша автоматика сама выбирает курьера под пакет. Ручной промежуточный
шаг — лишний запрос и гонка с лимитом курьеров между двумя вызовами.

## 2. Защита от дублей при создании пакета — **критично**

При сетевом таймауте клиент повторяет запрос, не зная, создался ли пакет —
получается дубль посылки. Функционально нужно: возможность передать свой
внешний идентификатор (external_id) или ключ идемпотентности — повтор с тем
же значением возвращает уже созданный пакет, а не создаёт второй.

Минимальная альтернатива: возможность найти пакет по трек-номеру (см. п. 5) —
тогда дубль можно обнаружить самим.

## 3. Полная история посылок

Сейчас список посылок отдаёт максимум 500 записей — всё старше через API
недоступно. Функционально нужно: доступ ко всей истории — постраничная
выборка (лимит/смещение) и/или фильтры по курьеру, статусу, периоду дат.

## 4. Актуальный список схем оплаты (pay_option)

Допустимые значения `pay_option` известны только из документации, панель
валидирует их жёстко. Когда на панели появляется новая схема — клиенты
узнают об этом ошибкой 400. Функционально нужно: способ узнать через API,
какие схемы оплаты доступны нашему аккаунту прямо сейчас.

## 5. Получение одной посылки / поиск по треку

Сейчас чтобы найти посылку по трек-номеру или обновить данные одной посылки,
приходится тянуть весь список. Функционально нужно: получить посылку по её
id и/или найти по трек-номеру.

## 6. Полный перечень статусов

В документации «`new`, `shipped`, `sent` и т.д.» — на практике приходят и
другие (`checked`, `received`, ...). Функционально нужно: полный список
возможных статусов посылок и курьеров и их переходы (документом или методом).

## 7. Снятие курьера

Добавить курьера через API можно, снять — нельзя (только через
поддержку/веб). Функционально нужно: обратная операция — убрать курьера со
своего аккаунта.

## 8. Комментарий к существующей посылке

Комментарий для admin/support можно передать только при создании посылки.
Функционально нужно: добавлять комментарий к уже созданной посылке.

## 9. Архивные курьеры

Сейчас архивные курьеры безмолвно исключаются из списка наших курьеров.
Функционально нужно: возможность запросить список включая архивных.

## 10. Формат файлов этикеток

Этикетки приходят в base64 без указания формата — предполагаем PDF наугад.
Функционально нужно: знать формат/имя файла (pdf/zpl/png) в ответе.

## 11. Уведомления о событиях (вебхуки) — стратегически

Сейчас узнаём об изменениях только периодическими опросами. Функционально
нужно (если планируется): уведомления на наш URL о смене статуса посылки,
новом комментарии, новой этикетке, добавлении/снятии курьера. Готовы
обсудить формат.

## 12. Уведомления об изменениях самого API

Формат `tracks` в списке посылок уже менялся без предупреждения (массив
строк → массив объектов) — интеграции ломались на проде. Функционально
нужно: предупреждать об изменениях схем заранее (канал/рассылка/changelog),
в идеале — версионирование API.

## 13. Информация об аккаунте

О лимите курьеров узнаём только из ошибки 403 в момент добавления.
Функционально нужно: узнать по ключу — какой это аккаунт, какой лимит
курьеров и сколько сейчас занято.

## 14. Расскажите, что ещё есть в панели

Судя по данным, которые уже приходят в ответах API, в панели явно есть
разделы, до которых у stuffer-API доступа нет. Если они существуют —
нужен к ним доступ (хотя бы на чтение):

- **Баланс/выплаты** — посылки имеют цену и схемы оплаты (`%`, `50/50`),
  значит где-то считаются начисления. Нужно: баланс аккаунта, история
  начислений/выплат, суммы по посылкам.
- **История посылки** — лог смены статусов с датами (кто/когда изменил),
  а не только текущий статус.
- **Уведомления/сообщения** — комментарии admin/support приходят в посылках;
  возможно, есть отдельный центр уведомлений (новая этикетка, проблема с
  посылкой, ответ поддержки). Нужно: список непрочитанного.
- **Список магазинов и перевозчиков** — поля `shop` и `carrier` сейчас
  свободный текст; если в панели есть справочники допустимых значений —
  нужен к ним доступ.
- **Админский список курьеров** — в веб-панели наверняка есть полный список
  курьеров системы. Если у нашей роли есть права — нужен и такой метод
  (хотя бы количество свободных/занятых).

Просим: прислать полный перечень разделов/возможностей панели — отметим,
что из этого нужно в API.
