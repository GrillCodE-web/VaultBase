# Аутентификация и роли — VaultBase

**Версия:** 2.5.0
**Обновлено:** 2026-08-07

Документ описывает, как в приложении устроены вход, шифрование и роли пользователей.

---

## 1. Флоу входа

```
1. Активация лицензии  →  challenge-код обменивается на activation key на sync-сервере
2. Мастер-пароль       →  из него выводится ключ, которым расшифровывается база
3. Автовход (solo)     →  установка с одним пользователем входит сразу, без экрана логина
```

Порядок экранов в `App.jsx`: `activate` → `auth` (мастер-пароль) → `app`.

### Почему нет отдельного логина

Раньше был третий экран «логин/пароль пользователя». В соло-режиме он избыточен: доступ уже
защищён мастер-паролем, без которого базу не расшифровать. Поэтому после ввода мастер-ключа
приложение делает **автовход** (`try_auto_login`) и открывает интерфейс сразу.

Экран логина (`UserLogin.jsx`) появляется только если в базе **больше одного** активного
пользователя (командный/legacy-режим).

---

## 2. Мастер-пароль и шифрование

- Мастер-пароль **не хранится**. Из него через PBKDF2 (600 000 итераций) выводится ключ.
- Ключ шифрует чувствительные поля (номера карт, пароли и т.п.) алгоритмом AES-256-GCM.
- Ключ живёт только в памяти и **зануляется** (zeroize) при блокировке.
- Авто-блокировка по неактивности (30 минут) — приложение возвращается на экран мастер-ключа.

### Первый запуск

При первом старте создаётся один пользователь `admin` со **случайным 32-байтным паролем,
который нигде не сохраняется** (ни в лог, ни в файл — прежний `ADMIN_PASSWORD.txt` удалён).
Пароль не нужен: вход в соло-режиме идёт через мастер-ключ.

## 3. Роли: admin / operator

Роль определяется **лицензией**, а не задаётся вручную в приложении.

### Как это работает

1. В админ-панели sync-сервера у каждой лицензии есть поле `role` (`admin` или `operator`).
2. При активации (`POST /api/activate`) сервер возвращает `role` вместе с токеном.
3. Клиент сохраняет её в конфиг `license_role`.
4. При каждом старте вызывается `POST /api/verify`, который тоже возвращает `role` — если
   на сервере роль сменили, у клиента она обновится **при следующем запуске**.
5. `try_auto_login` / `resume_session` применяют `license_role` к локальному пользователю
   (перезаписывают его роль, если она отличается).

### Разница ролей

|                              | admin | operator         |
| ---------------------------- | ----- | ---------------- |
| Просмотр всех карт           | ✅    | ❌ (только свои) |
| Управление пользователями    | ✅    | ❌               |
| Аудит-лог                    | ✅    | ограниченно      |
| Взятие/передача карт, заказы | ✅    | по правам        |

Гранулярные права заданы в `models.rs` (модуль `perms`) и проверяются и на бэкенде
(`require_perm`), и на фронте (`hasPerm`). Полная карта «право → команды», а также
четыре права, которые объявлены, но ничего не делают — в [PERMISSIONS.md](PERMISSIONS.md).
