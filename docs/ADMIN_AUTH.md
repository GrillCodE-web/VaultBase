# Аутентификация админ-панели

Дата: 2026-08-07

## Что изменилось

Раньше вход в админ-панель шёл через HTTP Basic: сервер отдавал заголовок
`WWW-Authenticate: Basic`, а браузер показывал своё системное окно ввода
логина/пароля. Из этого следовали три проблемы:

1. Нативное окно нельзя оформить — оно выпадало из дизайна VaultBase.
2. Из него **нельзя выйти**: браузер кэширует Basic-креды до закрытия окна.
3. Пароль уходил на сервер в каждом запросе, а не один раз при входе.

Теперь есть страница входа и сессия на подписанной cookie. HTTP Basic
**сохранён** как второй способ — им пользуются скрипты (`check_all.py` и прочая
эксплуатация), и ломать их было нельзя.

## Как это работает

```
Браузер                          Сервер
   │
   ├─ GET  <admin>/               ─────►  requireAdmin: cookie нет, Basic нет
   │                              ◄─────  302 → <admin>/login?next=...
   │
   ├─ GET  <admin>/login          ─────►  отдаётся login.html (без авторизации)
   │
   ├─ POST <admin>/login          ─────►  credentialsValid() → issueSession()
   │      {username, password}    ◄─────  Set-Cookie: vb_admin=<payload>.<hmac>
   │
   └─ GET  <admin>/               ─────►  requireAdmin: cookie валидна → 200
```

Скрипт вместо этого шлёт `Authorization: Basic ...` и попадает в панель
напрямую, минуя редирект (`wantsJson()` отдаёт им JSON-401, а не HTML).

### Формат cookie

```
vb_admin = base64url({"u":"admin","exp":1754...}) . base64url(HMAC-SHA256)
```

Подпись проверяется через `crypto.timingSafeEqual`. Полезная нагрузка **не
шифруется** — в ней нет секретов, только имя и срок; от подделки защищает HMAC.

### Ключ подписи

```js
key = SHA256('vaultbase-admin-session:' + (SESSION_SECRET || ADMIN_PASS))
```

Ключ выводится из `ADMIN_PASS`, а не генерируется случайно. Это даёт бесплатную
инвалидацию: **сменили пароль администратора — все выданные сессии умерли**, без
хранилища сессий и без обхода списка. Полезно ровно сейчас, когда пароль
подлежит ротации.

Если такое поведение не нужно (например, чтобы плановая смена пароля не
выкидывала всех), задайте `SESSION_SECRET` — тогда сессии переживут ротацию.

Срок жизни сессии — 8 часов.

## Переменные окружения

| Переменная       | Обязательна | Назначение                                                                 |
| ---------------- | ----------- | -------------------------------------------------------------------------- |
| `ADMIN_PASS`     | да          | Пароль. Без неё админка отвечает `503`. Короче 12 символов — warning в лог |
| `ADMIN_USER`     | нет         | Логин, по умолчанию `admin`                                                |
| `ADMIN_PATH`     | нет         | Префикс монтирования панели                                                |
| `SESSION_SECRET` | нет         | Отвязывает сессии от `ADMIN_PASS` (см. выше)                               |
| `TRUST_PROXY`    | нет         | Значение `trust proxy`, по умолчанию `loopback` (см. ниже)                 |

## Побочная находка: сломанный rate limiting

Интеграционные тесты вскрыли отдельный баг, который к логину отношения не имеет,
но ломал **все шесть** ограничителей на сервере.

В `index.js` никогда не выставлялся `trust proxy`. За nginx это значит, что
`req.ip` для каждого запроса равен адресу прокси — то есть `127.0.0.1`. Все
клиенты попадают в одну корзину лимитера:

- `/activate`, `/verify`, `/sync`, `/footprint` — общий счётчик на весь мир;
- любой одиночный клиент мог выбрать лимит и заблокировать **всех** остальных;
- логи и события `admin_login_failed` писали адрес прокси вместо адреса атакующего.

Исправлено:

```js
app.set('trust proxy', process.env.TRUST_PROXY || 'loopback')
```

Именно `loopback`, а не `true`. При `true` Express верит любому входящему
заголовку `X-Forwarded-For`, и клиент подделывает свой IP произвольно — лимитер
обходится в одну строку. `loopback` доверяет только прокси на том же хосте.
Если nginx стоит на другой машине, задайте `TRUST_PROXY` (число хопов или адрес).

`express-rate-limit` умеет ловить небезопасную настройку и падает с
`ERR_ERL_PERMISSIVE_TRUST_PROXY` — именно так баг и обнаружился.

## Защита

| Механизм              | Реализация                                                                                            |
| --------------------- | ----------------------------------------------------------------------------------------------------- |
| Подбор пароля         | 10 попыток / 15 мин на IP; успешные не считаются, чтобы общий NAT не блокировал легитимного админа    |
| Кража cookie через JS | `HttpOnly`                                                                                            |
| CSRF                  | `SameSite=Strict`                                                                                     |
| Перехват в сети       | `Secure` — ставится при `req.secure` либо `x-forwarded-proto: https` (за nginx)                       |
| Подделка сессии       | HMAC-SHA256 + сравнение за constant time                                                              |
| Утечка по таймингу    | `timingSafeEqual` и на логине, и на проверке подписи; логин и пароль сверяются оба, без short-circuit |
| Открытый редирект     | `?next=` принимается только если это путь вида `/...` (не `//host`, не `\`)                           |

## Файлы

| Файл                           | Роль                                                                                                 |
| ------------------------------ | ---------------------------------------------------------------------------------------------------- |
| `auth.js`                      | Выпуск/проверка сессий, работа с cookie, сверка кредов. Только встроенный `crypto`, без зависимостей |
| `routes/admin-auth.js`         | `GET /login`, `POST /login`, `POST /logout`                                                          |
| `admin/login.html`             | Страница входа                                                                                       |
| `middleware.js`                | `requireAdmin` — cookie **или** Basic                                                                |
| `test/auth.test.js`            | 14 тестов на `node:test` — криптография                                                              |
| `test/admin-auth.http.test.js` | 17 тестов — реальные HTTP-запросы                                                                    |

`requireBasicAuth` переименован в `requireAdmin` (`middleware.js`, `index.js`,
`routes/admin-api.js`, `routes/upload.js`) — имя перестало отражать суть, раз
способов входа теперь два.

## Порядок монтирования

```js
app.use(ADMIN_PATH,             require('./routes/admin-auth'));  // без охраны
app.use(`${ADMIN_PATH}/api`,    require('./routes/admin-api'));   // requireAdmin внутри
app.use(`${ADMIN_PATH}/upload`, require('./routes/upload'));      // requireAdmin внутри
app.use(ADMIN_PATH, requireAdmin, express.static(...));           // охрана здесь
```

Роуты логина монтируются **первыми и без охраны** — иначе `requireAdmin`
редиректил бы на `/login`, который сам требует авторизации: бесконечный цикл.

## Тесты

```bash
npm test --prefix cc-sync-server     # 31/31
```

Два уровня. `auth.test.js` (14) проверяет криптографию: успешный round-trip,
подмена payload, подмена подписи, битые cookie, истёкший срок, инвалидация при
смене `ADMIN_PASS` и `ADMIN_USER`, поведение без `ADMIN_PASS`, `SESSION_SECRET`,
пароль с двоеточиями в Basic, выбор нужной cookie среди нескольких, атрибуты.

`admin-auth.http.test.js` (17) поднимает Express с тем же порядком монтирования,
что и `index.js`, и ходит по нему настоящими запросами — то, что юнит-тесты
проверить не могут: отсутствие цикла редиректов, ветка «редирект против JSON-401»,
`Secure` при `X-Forwarded-Proto: https`, живучесть Basic для скриптов, выход,
инвалидация при ротации пароля и что `WWW-Authenticate` больше не отдаётся.
DB-роутеры туда не подключаются, поэтому набор идёт без скомпилированного
`better-sqlite3`.

Скрипт был `node --test test/` — Node 24 пытается резолвить это как модуль и
падает с `MODULE_NOT_FOUND`. Теперь `node --test "test/**/*.test.js"`.

`vitest.config.js` исключает `cc-sync-server/**`: серверные тесты идут на
встроенном раннере Node, и vitest на них падал с «No test suite found».

## Развёртывание

Ротация `ADMIN_PASS` разлогинит всех — это ожидаемо. Дополнительных шагов
миграции нет: старые Basic-креды продолжают работать, cookie появляется сама при
первом входе через форму.

Проверьте, что nginx передаёт заголовки, иначе `Secure` не выставится и
лимитеры снова увидят один IP:

```nginx
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

**Это не проверено.** В репозитории лежат только конфиги для
`pub-www.otpmanager.pro` (`deploy_full.py`, `deploy_ssl.py`), и они отдают
статику без `proxy_pass`. Конфиг `sec201-www`, который проксирует на Node и
перед которым реально стоит админка, в репозиторий не попал — его надо взять с
сервера (`/etc/nginx/sites-enabled/`) и убедиться, что оба заголовка на месте.

Если nginx и Node на **разных** машинах, `loopback` не подойдёт — задайте
`TRUST_PROXY`.

### Известное ограничение сборки

`better-sqlite3@9.6.0` не имеет готовых бинарников под Node 24 и на Windows без
MSVC собирается с ошибкой `node-gyp`. Тесты аутентификации от этого не зависят
(DB-роутеры в них не монтируются), но **полный запуск сервера локально на Node 24
невозможен**. Варианты: Node 20 LTS (совпадает с `engines`), либо апгрейд
`better-sqlite3` до версии с prebuild под 24. На сервере вопрос не стоит, если
там Node 20.
