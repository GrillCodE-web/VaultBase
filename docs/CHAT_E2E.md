# VaultBase — E2E-шифрованная переписка

Версия 1.0, 2026-08-30. Отдельный контур из контракта
[REDESIGN_05_PLAN.md](REDESIGN_05_PLAN.md). Требование пользователя: «ебать какую
шифрованную безопасную без утечек» — встроенный чат между всеми, кто есть в
приложении (менеджер ↔ воркеры, воркер ↔ воркер, общая комната).

## 0. Принцип

Сервер — тупой ретранслятор шифротекста. Он **не может** прочитать ни одного
сообщения: не хранит приватных ключей, не участвует в согласовании секретов.
Компрометация сервера = утечка зашифрованных блобов, которые без ключей мертвы.

## 1. Крипто-фундамент (уже есть в коде)

В MGR-016 вкатились **`worker_keys` с X25519** (видно в git: worker_keys +
запечатанные срезы карт). На этом же примитиве строим чат — ничего нового
заводить не нужно:

- **X25519** — обмен ключами (ECDH) между отправителем и получателем.
- **XSalsa20-Poly1305** (или AES-256-GCM — тот же уровень, что `encryption.rs`
  полей БД) — шифрование тела сообщения симметричным сессионным ключом.
- Каждое сообщение: эфемерная пара X25519 → сессионный ключ → AEAD → в БД
  ложится только `{ephemeral_pub, nonce, ciphertext}`. Forward secrecy на
  уровне сообщения.

## 2. Ключи

- Приватный ключ юзера **никогда не покидает устройство**: генерируется локально,
  хранится в SQLCipher-БД, зашифрованной мастер-паролем (PBKDF2 600k — уже есть).
- Публичный ключ публикуется на сервер при регистрации (эндпоинт worker_keys
  уже существует).
- Верификация отпечатков (опционально, по требованию): 6-значный код из
  SHA-256 обоих публичных ключей — сверка голосом/лично против MitM на сервере.

## 3. Модель сообщений

- **1:1** — прямой ECDH между двумя юзерами.
- **Общая комната** — sender keys: у автора симметричный ключ комнаты, который он
  раздаёт каждому участнику, зашифровав его X25519-ключом этого участника.
  Новый участник получает ключ с момента входа (старая история ему недоступна —
  это фича, не баг).
- **Контекстная привязка**: сообщение может ссылаться на ордер/карту/дропа
  («к ордеру #4823») — ссылка хранится в метаданных вне шифротекста (id сущности
  не секрет, содержимое — секрет).
- **TTL**: авто-удаление сообщений через N часов/дней (настраивается на комнату).
  Таймер работает и на клиенте, и мягкий — на сервере (сервер чистит блобы по
  истечении, не читая их).

## 4. Что видит сервер (и это честно зафиксировано)

| Видит                                     | Не видит                                    |
| ----------------------------------------- | ------------------------------------------- |
| Кто кому пишет (метаданные маршрутизации) | Содержимое сообщений                        |
| Время отправки                            | Приложенные файлы (шифруются тем же ключом) |
| Размер блоба                              | Имена сущностей в ссылках (только id)       |
| Публичные ключи                           | Приватные ключи                             |

Метаданные маршрутизации нельзя скрыть без onion-маршрутизации — это осознанный
компромисс десктопного приложения, а не Tor-релея.

## 5. Паник-стойкость

- **Panic-wipe** сносит приватные ключи → вся история переписки мертва навсегда,
  даже если сервер скомпрометирован позже. Это прямое следствие forward secrecy.
- Автоблокировка по idle (useIdleTimer уже есть) → ключи в памяти затираются,
  разблокировка заново требует мастер-пароль.
- Нет логирования тел сообщений на клиенте (соответствует правилу из
  docs/README.md форензик-карты: plaintext-логи не должны содержать переписку).

## 6. UI (в языке редизайна 05)

- Отдельный пункт сайдбара «Чат» (группа Система) со счётчиком непрочитанного.
- Список комнат слева, лента справа — как IMAP-страница, паттерн уже знаком.
- Индикатор шифрования в шапке комнаты: замок + «E2E · ключ верифицирован /
  не верифицирован».
- Встроить в единый инспектор: ордер → вкладка «Обсуждение» рядом с таймлайном.
- Уведомления — через центр уведомлений (п.8 второй порции), push через
  нативный notify Tauri.

## 7. Зависимости

- `worker_keys` (X25519) — **готово** (MGR-016, backend-сессия).
- Клиентская крипто-обвязка (генерация эфемерных пар, AEAD) — `src-tauri/`,
  стыкуем с backend-сессией.
- Транспорт — существующий `cc-sync-server` (WebSocket), новый тип сообщения
  `chat_blob`. Сервер менять почти не нужно: он и так ретранслирует opaque-сообщения.

## 8. Чего чат НЕ делает

- Не звонки, не видео — только текст и файлы.
- Не поиск по содержимому на сервере (невозможно с E2E — поиск локальный, по
  расшифрованному кэшу).
- Не восстановление истории на новом устройстве (ключи не мигрируют — это
  осознанно, против угона аккаунта).
