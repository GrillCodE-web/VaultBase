# Редизайн логики: Профиль как рабочая сессия, Заказы как монитор

Цель: убрать путаницу «как этим пользоваться» — профиль становится контейнером заказов (создание в контексте, 2 поля вместо 9 шагов), страница Заказов — обзор/мониторинг без создания.

Готово, когда:

- `npm run build` и `npx eslint src` чистые (0 errors)
- Из профиля заказ создаётся одной формой (магазин+товар, дроп/email/proxy автоподстановка primary/последних)
- CreateOrderModal (9 шагов) удалён; Orders.jsx не содержит создания заказа
- Профиль без дропов визуально помечен, заказ из него нельзя начать без добавления дропа
- Repeat-подобный сценарий не смешивает профиль A с дропом профиля B
- Главная показывает инбокс «требуют действий» (declined/зависшие треки/delivered-незакрытые) + карточки профилей

Границы: только воркер-приложение (src/). Без бэкенд-схемы: новых таблиц нет, используем существующие команды get_profiles/get_orders/create_order и т.д. Канбан-вид и автопарсинг буфера — НЕ входят (отдельная фича потом).

Не трогать: manager-app (только что отполирован), сервер, Rust-команды. Лёгкие добавления в Rust допустимы ТОЛЬКО если без них никак (предпочесть составление данных на фронте).

Риски: удаление CreateOrderModal — потеря risk-check и шаблонов заказов; митигация — компактный risk-badge в новой форме, шаблоны переносим в неё же. Большой дифф по Orders.jsx/Profiles.jsx — держать публичные пропсы и маршруты, чтобы не сломать ссылки из других страниц (navigate('orders', ...) и т.п.).
