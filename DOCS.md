# CC Manager — Полная документация

## Что это за приложение

CC Manager — это десктопное CRM-приложение для управления кредитными картами, профилями покупателей, заказами и магазинами. Все данные хранятся локально в зашифрованной SQLite базе на диске пользователя. Приложение работает офлайн — сетевое подключение используется только для фоновых задач.

Приложение написано на **Tauri** (Rust бэкенд) + **React** фронтенд. Фронтенд общается с бэкендом через IPC (межпроцессное взаимодействие Tauri через `invoke()`). Внешние сетевые запросы:
- **BIN enrichment** — iinapi.com (опционально)
- **ZIP-lookup** — zippopotam.us (опционально)
- **Сервер синхронизации** — лицензирование, footprint sync, автообновление (требуется при первом запуске, далее офлайн-режим поддерживается)

---

## Для чего используется

Полный цикл работы с кредитными картами — от импорта дампа до отслеживания доставки:

1. **Импорт** — вставить дамп карт в любом формате, система автоматически распознаёт колонки
2. **Обогащение** — BIN lookup добавляет банк, тип, уровень карты автоматически
3. **Профили** — связка «карта + дроп-адрес». Один профиль = одна личность для покупки
4. **Email Pool** — пул собственных ящиков, каждый используется только в одном магазине
5. **Прокси** — пул IP-адресов, отслеживание где каждый засветился
6. **Заказы** — оформление с Risk Check: система предупреждает если email/дроп/прокси/BIN уже засвечен в этом магазине
7. **Anti-Fraud** — footprints синхронизируются между всеми пользователями через сервер
8. **IMAP** — автоматически читает письма, вытаскивает трек-номера, обновляет статусы заказов
9. **Аналитика** — Dashboard показывает что работает прямо сейчас: какие банки и магазины дают результат

## Технологический стек

**Frontend**
- React 18 + Vite
- Tailwind CSS (тёмная тема, кастомные компоненты)
- lucide-react (иконки)
- Intl/i18n: самописный хук `useLang`, два языка — EN и RU

**Backend (Rust)**
- Tauri v1 — десктопная оболочка, IPC, нативные диалоги
- rusqlite (bundled) — SQLite без внешней зависимости
- AES-256-GCM — шифрование полей в БД
- bcrypt — хэширование мастер-пароля
- SHA-256 — деривация ключа шифрования
- ureq — HTTP клиент (BIN API, ZIP API)
- uuid — генерация ID для профилей
- chrono — работа с датами
- regex — парсинг форматов карт

### Auth — Аутентификация и блокировка

**Что это:** Мастер-пароль защищает все данные в приложении. Без пароля данные в БД нечитаемы — они зашифрованы AES-256-GCM.

**Первый запуск (Setup):**
Если `~/.config/cc-manager/auth.json` не существует — приложение открывает экран создания пароля. Пользователь задаёт мастер-пароль. Из него и соли генерируется ключ шифрования, который устанавливается в память. Хэш пароля (bcrypt) сохраняется в `auth.json`.

**Разблокировка (Unlock):**
При повторном запуске приложение стартует в locked-режиме. Пользователь вводит пароль → пароль проверяется по bcrypt-хэшу → ключ шифрования восстанавливается в памяти → данные становятся читаемы.

**Блокировка (Lock):**
Кнопка в сайдбаре. Ключ шифрования вытирается из памяти. Данные в БД остаются, но прочитать их без пароля невозможно. При следующем `invoke()` к данным будет ошибка.

**Смена пароля:**
Доступна в Settings. Требует текущий пароль + новый (мин. 12 символов, строчная + заглавная + цифра). При смене пароля **все зашифрованные поля в БД перешифровываются** со старого ключа на новый — транзакционно, через `db.reencrypt_all()`.

**Требования к паролю:** минимум 12 символов, хотя бы одна заглавная буква, одна строчная, одна цифра.

### CC — Кредитные карты

**Что это:** Основная сущность. Хранение, управление и работа с картами.

#### Поля карты

| Поле | Описание |
|---|---|
| `card_number` | Номер карты (зашифрован в БД) |
| `expiry_date` | Срок действия MM/YY или MM/YYYY |
| `cvv` | CVV/CVC (зашифрован) |
| `holder_name` | Имя держателя |
| `billing_address` | Платёжный адрес |
| `city`, `state`, `zip`, `country` | Платёжный адрес (разбитый) |
| `phone` | Телефон держателя |
| `email` | Email держателя |
| `ip_address` | IP адрес (из дампа) |
| `bin` | Первые 6 цифр карты |
| `bank_name` | Банк эмитент (заполняется через BIN enrichment) |
| `card_type` | Visa / Mastercard / Amex и т.д. |
| `card_level` | Classic / Gold / Platinum / Black и т.д. |
| `status` | Текущий статус карты |
| `source` | Откуда получена карта (домен/источник). Задаётся пользователем перед импортом в поле «Source label» — например `nike-dump-jan` или `shop.com`. Если не указан — автоматически подставляется `dump`. |
| `notes` | Заметки |

#### Статусы карт

- `free` — свободная, не используется ни в одном профиле (зелёный)
- `in_use` — привязана к активному профилю (фиолетовый)
- `dead` — заблокирована / не работает (красный)
- `archive` — архив (серый)

#### Таблица карт

Колонки настраиваются — кнопка «Columns» открывает панель видимости колонок. Настройки сохраняются в таблице `config` в БД. Все колонки кликабельны для сортировки.

Два режима отображения:
- **Normal** — полные строки
- **Compact** — уплотнённое отображение, больше строк на экране

> Compact режим реализован только для таблицы CC. Таблицы Profiles и Orders используют только Normal режим.

По умолчанию: `card_number`, `bin/bank`, `type`, `holder`, `country`, `source`, `status`, `orders`, `revenue`, `notes`, `actions`.

Номер карты в таблице маскируется: `****-****-****-1234`. Expiry и тип карты отображаются открыто — они не чувствительны. CVV скрыт. Кнопка **Reveal** открывает полный номер карты и CVV для конкретной строки.

#### Фильтры и поиск

- Статус (All / Free / In Use / Dead / Archive)
- Страна (текстовый ввод, например `US`, `GB`)
- Банк (текстовый ввод)
- Источник / домен (текстовый ввод — домен из дампа или `dump` если не указан)
- Диапазон дат создания (от / до)
- Поиск по номеру карты, имени держателя, email

Пагинация: 50 карт на страницу.

**Важно:** фильтры сбрасываются при уходе со страницы. Нажатие кнопки Reset или очистка поля = фильтр снят, при возврате на страницу — чистое состояние.

#### Действия с картой

Каждая карта в таблице имеет меню действий:

- **Reveal / Hide** — показать / скрыть полный номер карты и CVV
- **Copy number** — скопировать номер карты в буфер
- **Copy full data** — скопировать карту целиком в формате `number|expiry|cvv|holder|email|phone|address|city|state|country|zip`
- **Edit notes** — редактировать заметку прямо в строке таблицы
- **Create profile** — быстро создать профиль из этой карты (автоматически заполняет имя и страну из данных карты)
- **Mark Free / Mark Dead** — изменить статус (при смене на Dead — запрашивает подтверждение)
- **Delete** — удалить карту (с подтверждением)

#### Массовые операции

Чекбоксы в начале каждой строки + чекбокс «Выбрать все» в заголовке. При выборе нескольких карт появляется панель:

- **Mark Free** — массово перевести в free
- **Mark Dead** — массово перевести в dead
- **Export Selected** — экспортировать выбранные карты в TXT или CSV
- **Delete** — массово удалить (с подтверждением)

#### Импорт карт

Кнопка **Import** открывает 3-шаговый модальный диалог:

**Шаг 1 — Ввод данных:**
Текстовое поле куда вставляется дамп карт в любом формате. Поддерживаемые разделители: `|`, `,`, `\t` (таб), `;`, пробел. Пример форматов:
```
4111111111111111|12/26|123|John Doe|john@email.com|555-0100|123 Main St|New York|NY|US|10001
4111111111111111,12/26,123,John Doe,john@email.com
IP: 1.2.3.4 | Data: 4111111111111111|12/26|123
```

**Шаг 2 — Preview:**
Бэкенд автоматически определяет разделитель и маппит колонки. Показывается таблица с первыми строками дампа, где каждой колонке назначено поле. Автодетектированные маппинги подсвечены зелёным с пометкой «auto».

**Шаг 3 — Mapping:**
Всегда показывается после preview — пользователь видит автоопределённые колонки и может вручную переназначить каждую через выпадающий список. Автодетект предлагает, финальное слово всегда за пользователем.

Каждая колонка показывается как:
```
Col 0: [card_number ▼]  → 4111111111111111
Col 1: [expiry_date ▼]  → 12/26
Col 2: [cvv ▼]          → 123
Col 3: [skip ▼]         → нераспознанное поле
```
Варианты в выпадающем списке: все поля карты + `skip` (пропустить колонку).

После подтверждения — импорт. Дубликаты (по номеру карты) автоматически пропускаются. Результат: `Imported N card(s) (M duplicates skipped)`.

После успешного импорта — автоматически запускается **silent BIN enrichment** (если ключ IINAPI задан): обогащение проходит в фоне и обновляет таблицу если что-то нашлось. Заполняются: `bank_name`, `card_type`, `card_level`, `country` — для всех импортированных карт у которых эти поля пустые.

**Импорт из файла:**
Кнопка **From File** — открывает нативный диалог выбора файла (`.txt`, `.csv`, `.log`). Файл читается бэкендом и проходит те же 3 шага что и текстовый импорт: парсинг → preview с маппингом → подтверждение. Логика идентична.

#### Экспорт карт

- **TXT** — экспорт в текстовый файл в формате `number|expiry|cvv|holder|...` (с учётом текущих фильтров)
- **CSV** — экспорт в CSV с заголовками (с учётом текущих фильтров)

Открывается нативный диалог сохранения файла.

#### BIN Enrichment

Кнопка **Enrich BINs** — запускает обогащение всех карт данными банка через [iinapi.com](https://iinapi.com).

Процесс:
1. Из БД берутся все BINы (первые 6 цифр) у карт без данных банка
2. Дедупликация BINов
3. Для каждого BIN — запрос к `api.iinapi.com/iin?key=...&digits=BIN`
4. Результат: `bank_name`, `card_type`, `card_level`, `country` эмитента
5. BIN кешируется в таблице `bins` в БД
6. Данные применяются ко всем картам с этим BIN
7. Между запросами — задержка 200мс (rate limiting)

Ключ IINAPI настраивается в Settings → хранится в зашифрованной БД.

Если ключ не задан — показывается ошибка «IINAPI key not set — go to Settings».

#### Дубликаты

Кнопка **Duplicates** — находит карты с одинаковым номером и показывает их в модальном окне. Позволяет увидеть сколько раз дублируется каждая карта.

### Profiles — Профили

**Что это:** Профиль — это рабочая единица. Связка «кредитная карта + один или несколько адресов доставки». Профиль отражает одну «личность» для совершения покупок.

**Когда создаётся профиль:** После того как карта импортирована и проверена — из неё создаётся профиль. Профиль наследует данные карты (имя держателя, страну) но может иметь отдельные адреса доставки (дропы), отличные от платёжного адреса карты.

**Workflow заполнения на сайте магазина:**
```
Email на сайте     → свой email из пула (не из карты)
Billing Name       → имя держателя карты
Billing Address    → адрес карты (из дампа)
Shipping Name      → имя держателя карты (совпадает с billing)
Shipping Address   → адрес дропа
Card Number        → номер карты
Expiry / CVV       → из карты
```

Email выбирается из пула собственных ящиков (см. Email Pool). Правило: 1 email = 1 магазин навсегда. Система автоматически предлагает незасвеченный email при создании заказа.

#### Создание профиля

Два способа открыть форму создания:
- Кнопка **Create Profile** в разделе Profiles
- Кнопка **Create Profile** прямо в строке карты в таблице CC — открывает ту же модальную форму, но карта уже предвыбрана и биллинг заполнен автоматически

Форма — единое модальное окно, всё сразу, без шагов и переходов между страницами.

**Блок 1 — Выбор карты (Smart Card Picker):**

Поле с живым автокомплитом — не статический выпадающий список:
- Вводишь имя держателя, последние 4 цифры (`1234`) или ZIP карты
- Сразу показываются совпадения (до 10 карт) с превью: `****1234 — John Doe — Chase Visa Gold — New York NY 10001`
- Выбрал → все биллинговые поля в Блоке 2 заполняются автоматически

**ZIP-radius подбор карты:**
Кнопка **📍 Find Near ZIP** рядом с полем поиска. Открывает мини-диалог: вводишь ZIP дропа (адреса доставки) → система находит все `free` карты у которых биллинговый ZIP находится в радиусе **100 миль** от введённого (расчёт по координатам через кеш `zippopotam.us`, формула Haversine). Список отсортирован по дистанции — ближайшие сверху. Показывается расстояние: `Chase ****4521 — 12 mi — Hoboken NJ`. Это снижает фрод-риск: billing и shipping адреса в одном регионе — норма для магазина.

**Блок 2 — Billing Address:**
Заполняется автоматически из данных выбранной карты. Все поля редактируемы.

**Блок 3 — Shipping Addresses (Drops):**
Прямо в форме создания — не в отдельном шаге. Одна пустая строка дропа по умолчанию. Кнопка **+ Add Drop** добавляет новую строку. Каждый дроп: имя получателя, адрес, город, штат, ZIP, страна, телефон, чекбокс `Primary`. Первый дроп автоматически помечается как Primary.

Дропы не обязательны при создании — можно добавить позже через детальный просмотр профиля. Но форма позволяет добавить любое количество сразу.

**Блок 4 — Название и заметки:**
- **Название** — автогенерируется: `FirstName LastName ••1234`. Можно изменить.
- Заметки

При создании профиля карта автоматически переводится в статус `in_use`.

**Cascade карта → профиль:**
Когда карта переходит в статус `dead` — привязанный профиль автоматически переводится в `archive`. История заказов профиля сохраняется полностью, статистика не теряется. Профиль из архива можно восстановить если нужно (например перебив карты через Duplicate).

**Cascade удаление профиля → карта:**
При удалении профиля вручную — привязанная карта автоматически возвращается в статус `free`. Диалог подтверждения явно сообщает: *«Удалить профиль и N заказов? Карта вернётся в статус Free.»*

#### Таблица профилей

Показывает для каждого профиля:
- UUID профиля (маскированный последними символами)
- Данные карты: маскированный номер `****1234`, имя держателя, банк
- Страна и статус карты
- Статус профиля
- Количество заказов и отгрузок

Фильтры: по статусу профиля, **без дропа** (профили у которых нет ни одного дропа), текстовый поиск, диапазон дат создания. Пагинация 50 на страницу.

#### Массовые операции с профилями

Чекбоксы в начале каждой строки + «Выбрать все». При выборе нескольких профилей появляется панель:
- **Set Active** — массово перевести в active
- **Set Dead** — массово перевести в dead (с подтверждением)
- **Delete** — массово удалить (с подтверждением)

#### Детальный просмотр профиля

Клик по профилю открывает боковую панель / детальное представление с секциями:

**Card Data:**
- Полный номер карты (маскированный), expiry, CVV
- Имя держателя, email, телефон
- Банк, тип карты, уровень
- Кнопки копирования для каждого поля

**Billing Address:**
- Платёжный адрес из данных карты
- Кнопка **Copy Billing** — копирует адрес в буфер в формате:
  ```
  Name: John Doe
  Address: 123 Main St
  City: New York
  State: NY
  Zip: 10001
  Country: US
  Phone: 555-0100
  ```

**Shipping Addresses (Drops):**
- Список всех дроп-адресов
- Кнопка **Add Drop** — добавить новый адрес доставки
- Для каждого дропа: кнопка **Copy Primary** — копировать в буфер
- Кнопка удаления дропа

**Profile Status:**
- Текущий статус: active / dead / archive
- Переключатель статуса

**Orders:**
- Список заказов этого профиля (order_number, статус, сумма, дата)
- Кнопка **+ New Order** прямо внутри профиля — открывает форму создания заказа с уже выбранным профилем, не нужно переходить в раздел Orders

#### Быстрые действия на строке профиля

- **Copy** — копировать весь профиль (приоритет: primary дроп, затем биллинг карты)
- **Copy Card** — скопировать данные карты в pipe-формате `number|expiry|cvv|...`
- **Copy Billing** — скопировать платёжный адрес
- **Copy Shipping** — скопировать primary дроп-адрес
- **Float Window** — открыть профиль в плавающем мини-окне (см. ниже)
- **Duplicate** — создать дубликат профиля с новой картой. Система автоматически подбирает карту `free` которая не засвечена в тех же магазинах что и текущий профиль — можно поменять вручную из списка. Если дропы уже засветились — предупреждение: «X drops already used in shops — copy anyway or create without drops?»
- **Create Order** — быстро создать пустой заказ по этому профилю
- **Delete** — удалить профиль и все его заказы

#### Float Window — Плавающее окно профиля

Открывает профиль в отдельном **нативном окне Tauri** (620×360px) поверх всех других окон (`always_on_top: true`). Это именно отдельное OS-окно — не React-оверлей — что позволяет ему висеть поверх браузера пока пользователь заполняет форму на сайте магазина.

**Техническая реализация:** отдельная точка входа Vite (`float.html`). `profile_id` передаётся через URL-параметр (`/float?id=uuid`). Данные загружаются через стандартный `invoke()`. При открытии float-окна главное окно остаётся активным.

Float-окно содержит три вкладки:
- **Card** — номер, expiry, CVV, имя, email, телефон, банк, тип — каждое поле с кнопкой копирования
- **Billing** — платёжный адрес с кнопкой «Copy Billing»
- **Shipping** — primary дроп-адрес с кнопкой «Copy Shipping»

Каждое поле копируется одним кликом. После копирования иконка мигает зелёной галочкой на 1.8 секунды.

**Кнопки результата** (внизу float-окна) — меняют статус **уже существующего** заказа:
- **✓ Success** — заказ переходит в `processing` (магазин принял). Открывается мини-диалог для номера заказа если ещё не введён.
- **✗ Decline** — заказ переходит в `decline`. Появляется предложение перевести карту в `dead` (с подтверждением).

**⚠️ Известная проблема:** при первом открытии может показываться белый экран — требуется небольшая задержка инициализации окна перед загрузкой данных профиля.

**Risk Check в float-окне:**
Показывает компактный статус риска: 🟢 / 🟡 / 🔴 относительно последнего выбранного магазина. Клик по индикатору разворачивает список предупреждений.

**Кнопки Success/Decline** применяются к последнему активному заказу профиля (статус `pending`). Если таких заказов несколько — показывается выпадающий список для выбора нужного.

#### Дубликаты профилей

Кнопка **Find Duplicates** в таблице профилей — находит профили привязанные к одной и той же карте. Показывает список в модальном окне.

### Drops — Адреса доставки

**Что это:** Дроп-адрес — это адрес доставки, отличный от платёжного адреса карты. К одному профилю можно добавить несколько дропов.

**Поля:** имя получателя, адрес, город, штат, ZIP, страна, телефон, флаг `is_primary`.

**Primary дроп** — отмечается галочкой, используется по умолчанию при копировании адреса доставки и в float-окне.

**Правило 1 дроп = 1 магазин:** один дроп-адрес нельзя использовать в одном магазине дважды — это фрод-сигнал. При создании заказа система проверяет через footprint и предупреждает если дроп уже засветился в этом магазине.

ZIP-lookup при создании дропа убран. Автодополнение города/штата по ZIP работает только при импорте карт (см. парсер).

**Импорт дропов из текста:**
Кнопка **Import Drops** находится в детальном просмотре профиля (секция Shipping Addresses). Вставить список адресов в формате:
```
name|address|city|state|zip|country|phone
John Doe|123 Main St|New York|NY|10001|US|555-0100
```
Аналогично импорту карт: preview → маппинг → подтверждение.

**Поиск дубликатов дропов:**
Кнопка **Find Duplicates** — находит одинаковые адреса привязанные к разным профилям. Это потенциальный фрод-сигнал — один физический адрес на нескольких людей.

### Email Pool — Пул собственных email-ящиков

**Что это:** Список собственных email-адресов которые используются при оформлении заказов на сайтах магазинов (не email из дампа карты).

**Правило:** 1 email = 1 магазин навсегда. Если email засветился в Nike — он никогда не используется в Nike снова. В других магазинах — можно.

**Интеграция с IMAP:** email из пула можно подключить как IMAP ящик — тогда приложение будет автоматически читать письма-подтверждения и обновлять статусы заказов.

#### Поля email

| Поле | Описание |
|---|---|
| `email` | Адрес электронной почты |
| `label` | Название для удобства |
| `imap_account_id` | Привязка к IMAP ящику (опционально) |
| `notes` | Заметки |

#### Таблица email pool

Для каждого email показывается:
- Адрес и лейбл
- Список магазинов где уже использован (засвечен)
- Статус: **чистый** / **использован в N магазинах** / **заблокирован вручную**

#### Автоподбор при заказе

При выборе магазина в форме заказа — система автоматически предлагает незасвеченный email из пула. Можно поменять вручную. Если все email засвечены в этом магазине — показывается предупреждение.

Email с флагом `is_blocked: true` **исключаются из автоподбора** и не предлагаются пользователю. Заблокированный email можно выбрать только вручную — и только если пользователь явно знает что делает.

#### Новая таблица: email_pool

> **Связь с `imap_accounts`:** ссылка односторонняя — `email_pool.imap_account_id` → `imap_accounts`. Таблица `imap_accounts` не хранит FK обратно на `email_pool`. Это исключает circular reference: сначала создаётся IMAP ящик, затем email из пула привязывается к нему.

| Поле | Тип | Описание |
|---|---|---|
| `id` | INTEGER | PK |
| `email` | TEXT | Адрес (зашифрован) |
| `label` | TEXT | Название |
| `imap_account_id` | INTEGER | FK → imap_accounts (опционально) |
| `is_blocked` | BOOLEAN | Заблокирован вручную |
| `notes` | TEXT | Заметки |
| `created_at` | DATETIME | — |

**Email в footprint:** при создании заказа хэш email из пула записывается в `shop_footprints.email_hash`. Именно этот email (а не email из карты) отслеживается системой защиты.

### Orders — Заказы

**Что это:** Трекинг заказов. Каждый заказ привязан к профилю и опционально к магазину.

#### Создание заказа

Форма заказа:
- Выбор профиля (выпадающий список всех профилей)
- **Выбор магазина** — поле с живым автокомплитом. Начинаешь вводить название (`"ni"`) → сразу показывается список совпадений из твоего локального справочника (`Nike`, `Nine West`). Если магазина ещё нет — можно создать прямо здесь кнопкой **+ New Shop**, не уходя из формы заказа. При выборе магазина — рядом сразу отображаются его флаги (блокирует VPN, требует CVV match и т.д.) и Smart Suggestions. Список магазинов локальный — у каждого пользователя свой, без предустановок.
- **Выбор дропа** (выпадающий список дропов выбранного профиля; по умолчанию — primary дроп). Именно выбранный дроп хэшируется в footprint и сохраняется в `drop_id` заказа.
- Выбор email из пула (автоподбор незасвеченного — можно поменять)
- Выбор прокси (опционально — из пула прокси)
- Номер заказа (вводится вручную — берётся из подтверждения на сайте)
- Список товаров: название, SKU (опционально), количество, цена
- Итоговая сумма
- Заметки

Заказ можно создать также прямо из детального просмотра профиля — профиль предзаполняется автоматически.

Товары в заказе хранятся как JSON в одном поле. Количество строк товаров не ограничено — кнопка «Add Item» добавляет строку.

**Order Templates:** Если одинаковый набор товаров используется часто — его можно сохранить как шаблон (кнопка «Save as template», вводится имя + опционально тег магазина). Шаблоны глобальные — доступны для любого заказа. При выборе магазина в форме — шаблоны с тегом этого магазина показываются первыми. «Load template» → все товары подставляются автоматически.

#### Статусы заказов

| Статус | Цвет | Описание |
|---|---|---|
| `pending` | жёлтый | Заказ только создан |
| `processing` | оранжевый | Магазин принял, готовит к отправке |
| `shipped` | синий | Отправлен, есть трек-номер |
| `in_transit` | голубой | В пути (трекинг показывает движение) |
| `delivered` | зелёный | Доставлен получателю |
| `on_hold` | фиолетовый | Магазин задержал / на паузе |
| `cancelled` | серый | Отменён магазином или пользователем |
| `refunded` | белый | Возврат денег |
| `decline` | красный | Карта задеклайнена |

**Flow статусов:**
```
pending → processing → shipped → in_transit → delivered
                    ↘ on_hold
                    ↘ cancelled
                    ↘ refunded
pending → decline (карта не прошла)
```

#### Отметить как Shipped

При переводе заказа в статус `shipped` — открывается дополнительный диалог где нужно ввести:
- Трек-номер
- Перевозчик (USPS, UPS, FedEx и т.д.)

Эти данные сохраняются в заказе и отображаются в таблице.

#### Таблица заказов

Колонки: номер заказа, профиль (имя держателя + последние 4 цифры карты), магазин, статус, сумма, трек-номер, дата создания.

Фильтры: по статусу, по магазину, диапазон дат создания, текстовый поиск. Пагинация 50 на страницу.

**Цветовая маркировка строк:**

| Статус | Цвет строки |
|---|---|
| `pending` | жёлтый |
| `processing` | оранжевый |
| `shipped` | синий |
| `in_transit` | голубой |
| `delivered` | зелёный |
| `on_hold` | фиолетовый |
| `cancelled` | серый |
| `refunded` | белый/нейтральный |
| `decline` | красный |

**Автосмена статуса карты при decline:**
При переводе заказа в `decline` — система предлагает перевести карту в `dead` (диалог с подтверждением). Решение за пользователем, но предложение появляется всегда. Карта не переводится автоматически — только по подтверждению.

При `cancelled` — карта НЕ переводится в dead автоматически (отмена не означает что карта плохая).

**Статус `refunded`** — деньги вернули. Карта и профиль остаются без изменений, заказ просто помечается как refunded. Это не означает что карта плохая.

**Ручная смена статусов:** любой статус можно установить вручную через меню в строке заказа. Flow (pending → processing → shipped...) — это рекомендованный путь, не жёсткое ограничение.

### Shops — Магазины

**Что это:** Справочник магазинов, в которых делаются заказы. Позволяет привязывать заказы к конкретным магазинам и отслеживать их эффективность.

#### Поля магазина

- Название
- **Domain** — нормализованный домен сайта (например `nike.com`). Обязательное поле. Используется как универсальный идентификатор при кросс-пользовательской синхронизации footprints. При создании магазина — извлекается автоматически из URL если URL введён.
- URL сайта (с кнопкой «Visit site» — открывает в браузере)

> Список магазинов локальный — у каждого пользователя свой. Предустановленных шаблонов нет, каждый создаёт свои магазины вручную. В полях выбора магазина (форма заказа) — живой автокомплит по локальному списку. Новый магазин можно создать прямо из формы заказа кнопкой **+ New Shop** не уходя со страницы.
- Категория (Electronics, Fashion, Sports и т.д.)
- Заметки (свободный текст)

**Структурированные правила магазина** (чекбоксы):
- ☐ Требует CVV match
- ☐ Блокирует VPN/proxy
- ☐ Телефон должен совпадать с биллингом
- ☐ Принимает Amex
- ☐ Требует верификацию адреса (AVS)
- ☐ Высокий риск отмены

Эти флаги отображаются как теги при выборе магазина в форме создания заказа — сразу видно особенности.

#### Статистика магазина

Для каждого магазина автоматически считается из таблицы заказов:
- Счётчики по всем статусам: Pending / Processing / Shipped / In Transit / Delivered / On Hold / Cancelled / Refunded / Declined
- Total orders
- Средний чек (avg_order_value)
- Конверсия (success_rate = delivered / total)
- % decline (decline / total)

#### Smart Suggestions — умные подсказки

На основе накопленной истории заказов система генерирует предупреждения при создании заказа:

```
⚠️ Этот магазин часто отменяет заказы с картами Chase (отмена 7 из 9)
⚠️ Visa Classic в этом магазине — 12% успеха (слабый результат)
```

#### Товары магазина (Products)

К каждому магазину можно добавить каталог товаров. Это удобно для арбитражных схем.

Поля товара:
- **ASIN** — артикул Amazon (обязательный)
- Название товара
- **Amazon Price** — цена на Amazon (закупочная)
- **Shop Price** — цена в данном магазине
- URL товара
- Заметки

Разница `shop_price - amazon_price` = маржа. Это помогает понимать профитность каждого товара.

## Anti-Fraud — Система защиты от пересечений

### Концепция

При каждом заказе все идентификаторы которые "засветились" в магазине записываются в локальную БД и синхронизируются на сервер. Перед созданием нового заказа система проверяет пересечения — чтобы не использовать одни и те же данные в одном магазине дважды.

Это работает **между всеми пользователями** через общий сервер — если один засветил дроп в Nike, второй получит предупреждение.

### Что составляет footprint одного заказа

Footprint записывается **в момент создания заказа** (статус `pending`) — вне зависимости от исхода. Decline не отменяет засветку: дроп, email и прокси считаются использованными в этом магазине навсегда.

При создании заказа система автоматически записывает:
- `shop_domain` — нормализованный домен магазина (например `nike.com`). Используется вместо локального `shop_id` для кросс-пользовательской синхронизации — домен одинаков у всех пользователей.
- `email_hash` — SHA-256 хэш email из **собственного пула** (не email карты)
- `ip_hash` — SHA-256 хэш IP адреса / прокси. Если прокси не выбран — пишется `NULL`. Реальный IP устройства не используется. Заказы без прокси не проверяются по IP.
- `drop_hash` — SHA-256 хэш **адреса доставки без имени получателя**: `address + city + state + zip + country`. Имя намеренно исключено — чтобы один и тот же физический адрес с разными именами давал одинаковый хэш.
- `bin` — первые 6 цифр карты
- `phone_hash` — хэш телефона держателя карты
- `name_hash` — хэш имени получателя на дропе

Хранятся **только хэши** — сами данные на сервер не уходят никогда.

### Risk Check при создании заказа

Перед созданием заказа — автоматическая проверка пересечений. Показывается блок **Risk Check**:

| Уровень | Условие |
|---|---|
| 🟢 Safe | Нет пересечений |
| 🟡 Warning | 1-2 пересечения (например email или BIN) |
| 🔴 High Risk | 3+ пересечений или критичные поля (IP, дроп) |

Примеры предупреждений:
```
⚠️ Email засветился в этом магазине (заказ #47, shipped)
⚠️ Этот дроп использован в этом магазине (заказ #31, decline)
🔴 Этот IP/прокси уже использовался в этом магазине (по хэшу)
```

**Режим офлайн:** при отсутствии подключения к серверу Risk Check выполняется только по локальной БД. Данные других пользователей в этом случае не учитываются. В блоке Risk Check показывается предупреждение: `⚠️ Offline — check is local only`.

Система не блокирует действие — только информирует. Решение за пользователем.

## Безопасность и шифрование

### Какие поля шифруются

Чувствительные поля карт хранятся в БД зашифрованными: номер карты, CVV, имя держателя, адрес, телефон, email, IP-адрес.

Незашифрованные поля (нужны для фильтрации/поиска через SQL): BIN, страна, банк, тип карты, статус, даты.

### Алгоритм шифрования

```
Ключ шифрования = SHA-256(password_bytes || salt_bytes || b"cc-manager-field-v2")
Шифрование = AES-256-GCM(key, random_nonce_12_bytes, plaintext)
Хранение в БД = Base64(nonce[12] || ciphertext)
```

Нonce генерируется случайным образом для каждой операции шифрования — одно и то же значение будет зашифровано по-разному каждый раз.

### Хранение пароля

Мастер-пароль **никогда** не хранится в открытом виде. В `auth.json` хранится только bcrypt-хэш с cost factor по умолчанию. Соль хранится отдельно — используется только для деривации ключа шифрования.

### Ключ шифрования в памяти

После разблокировки ключ живёт в `Arc<FieldEncryption>` внутри `Mutex<Database>` в AppState. При блокировке (`lock` команда) — `db.clear_encryption()` убирает ключ: `self.encryption = None`. Данные читать больше нельзя.

## Парсер CC (детально)

Файл: `src-tauri/src/parser.rs`

### Автодетектирование разделителя

Считает частоту каждого разделителя в первых строках. Победитель — тот чья частота наиболее стабильна по строкам (одинаковое число полей в каждой строке).

Поддерживаемые разделители: `|`, `,`, `\t`, `;`, пробел.

### Автомаппинг колонок

Для каждой колонки анализируется содержимое:

| Что распознаёт | Как |
|---|---|
| Номер карты | Luhn-алгоритм + длина 13-19 цифр |
| Expiry | Формат `MM/YY` или `MM/YYYY` |
| CVV | 3-4 цифры (если не похоже на другое) |
| Email | Содержит `@` и `.` |
| IP-адрес | Формат `N.N.N.N` |
| ZIP | 5 цифр (US) или короткие числовые строки |
| Телефон | Числа с дефисами/скобками, длина 10+ |
| Страна | 2-буквенный ISO код |

### Luhn-алгоритм

Валидация номеров карт при автодетектировании. Исключает случайные числовые строки от реальных номеров карт.

### ZIP-lookup и обогащение адреса при импорте

При разборе карты система автоматически пытается восстановить недостающие адресные поля:

| Есть | Нет | Действие |
|---|---|---|
| ZIP + country | city, state | Запрос к `zippopotam.us` → подставляет city и state |
| city | country | Определяется по BIN стране эмитента |
| — | zip, city, state | Поля остаются пустыми, заполняются вручную |

Результаты ZIP-lookup кешируются в `lazy_static!` HashMap на всё время сессии — повторные запросы для одного ZIP не делаются.

Кешированные координаты также используются для **ZIP-radius поиска карт** при создании профиля: система вычисляет расстояние между ZIP дропа и ZIP биллинга карты по формуле Haversine и отбирает карты в радиусе 100 миль.

### Preview режим

Перед финальным импортом парсер возвращает:
- `delimiter` — определённый разделитель
- `mapping` — предложенный маппинг колонок
- `preview_lines` — первые строки для показа пользователю
- `total_lines` — всего строк в тексте
- `parsed_count` — успешно распознанных строк
- `cards_found` — количество карт готовых к импорту

## IMAP — Почтовая автоматизация

**Статус:** 🚧 В разработке. При переходе в раздел показывается экран «Under Development».

### Назначение

IMAP раздел решает две задачи:
1. **Автоматически читать письма** — трек-номера, статусы заказов, подтверждения
2. **Управлять пулом email** — какие ящики чистые для каких магазинов

### Подключение ящиков

Добавить несколько IMAP ящиков (каждый = один email из пула):
- host, port, login, password (зашифрован AES-256-GCM)
- Проверка соединения при добавлении
- Автоматический polling каждые N минут (настраивается)
- Привязка к email в `email_pool`

### Парсинг писем-подтверждений

При получении нового письма система анализирует его и извлекает:
- Номер заказа (order number)
- Трек-номер (tracking number)
- Перевозчик (USPS / FedEx / UPS — автодетект)
- Статус (shipped / delivered / cancelled)

Сопоставление с заказом идёт по номеру заказа. Если найдено совпадение — заказ автоматически обновляется, статус меняется.

**Поведение при автоблокировке:** IMAP polling продолжает работать в фоне даже когда приложение заблокировано — ключ шифрования при блокировке стирается, поэтому найденные данные (трек-номера, статусы, номера заказов) **не записываются в БД сразу**, а накапливаются в in-memory буфере в Rust. При разблокировке все накопленные обновления применяются к заказам транзакционно и показывается уведомление о количестве обновлений.

### Трекинг по трек-номеру

После извлечения трек-номера — система запрашивает статус доставки:
- USPS → usps.com API
- FedEx → fedex.com API
- UPS → ups.com API

Статус обновляется автоматически: `shipped` → `in_transit` → `delivered`.

### Автоматические действия

| Письмо | Действие |
|---|---|
| Подтверждение заказа | Заказ → `processing`, номер заказа сохраняется |
| Письмо с трек-номером | Заказ → `shipped`, трек сохраняется |
| Трекинг показывает движение | Заказ → `in_transit` |
| Письмо о доставке | Заказ → `delivered` |
| Письмо об отмене | Заказ → `cancelled` |

### Таблица: imap_accounts

| Поле | Тип | Описание |
|---|---|---|
| `id` | INTEGER | PK |
| `label` | TEXT | Название ящика |
| `host` | TEXT | IMAP сервер |
| `port` | INTEGER | Порт (обычно 993) |
| `login` | TEXT | Логин |
| `password` | TEXT | Зашифрован AES-256-GCM |
| `poll_interval` | INTEGER | Интервал проверки (минуты) |
| `is_active` | BOOLEAN | Включён/выключен |
| `last_checked` | DATETIME | Последняя проверка |

> Связь с `email_pool` хранится на стороне `email_pool.imap_account_id` — не здесь.

## Фоновые потоки (Rust)

При старте приложения запускаются 4 фоновых потока:

| Поток | Интервал | Что делает |
|---|---|---|
| **sync_thread** | каждые 2 мин | Отправляет накопленные footprints на сервер пачкой |
| **autolock_thread** | каждые 30 сек | Проверяет таймер неактивности, блокирует если истёк |
| **imap_thread** | настраивается (мин. 1 мин) | Проверяет новые письма во всех активных IMAP ящиках |
| **tracking_thread** | каждые 30 мин | Обновляет статус доставки для заказов в shipped/in_transit через API перевозчиков |

Все потоки запускаются через `tauri::async_runtime::spawn`. При блокировке приложения:
- `sync_thread` — приостанавливается (нет токена для отправки)
- `autolock_thread` — продолжает работать
- `imap_thread` — продолжает работать, данные накапливаются
- `tracking_thread` — продолжает работать, обновления применяются после разблокировки

## Серверная синхронизация

### Архитектура

Сервер хранит **минимум данных** — только хэши засветок и лицензии. Никаких карт, имён, адресов.

```
VPS ($5/месяц)
├── HTTP сервер (Node.js / Python)
├── БД (PostgreSQL или SQLite)
│   ├── licenses — ключи активации
│   ├── footprints — хэши засветок по магазинам
│   └── versions — текущая версия приложения
└── Админ панель (простая HTML страница)
```

### Endpoints

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/activate` | Активация ключа, выдача токена |
| `POST` | `/verify` | Проверка токена при старте |
| `POST` | `/footprint` | Записать засветку (batch) |
| `POST` | `/check` | Проверить пересечения перед заказом |
| `GET` | `/version` | Текущая версия для автообновления |

### Offline-first синхронизация

Footprints сначала пишутся локально с флагом `synced: false`. Фоновый поток в Rust каждые 2 минуты отправляет всё накопленное на сервер пачкой.

```
Нет интернета → footprints копятся локально
Интернет появился → всё улетает пачкой → synced: true
```

На сервер уходит `shop_domain` (например `nike.com`) — **не** `shop_id`. Это гарантирует что footprints от разных пользователей по одному магазину корректно сопоставляются на сервере, даже если у них разные локальные `shop_id`.

Сервер дедуплицирует входящие записи по уникальному ключу `(shop_domain, hash_type, hash_value, user_token)` — повторная отправка одного footprint (например после restore из бэкапа) не создаёт дублей.

Приложение работает полностью офлайн. Синхронизация прозрачная и автоматическая.

### Принудительная отправка

Footprint отправляется **из Rust бэкенда**, не из фронтенда. Фронтенд не имеет возможности отключить синхронизацию. Единственный способ обойти — не создавать заказ.

## Система лицензирования

### Схема активации (Challenge-Response)

```
1. Приложение генерирует случайный Installation ID
2. Пользователь видит код: A3F9-BE21-44DC-7720
3. Пользователь отправляет код администратору
4. Администратор вводит код в админ панель
5. Сервер генерирует ответный ключ активации
6. Администратор отправляет ключ пользователю
7. Пользователь вводит ключ в приложение → активировано
```

Один Installation ID = один ответный ключ = одна установка.

### Экран активации

Показывается при первом запуске — до экрана мастер-пароля:

```
┌─────────────────────────────────┐
│  Activation Required            │
│                                 │
│  Your installation code:        │
│  A3F9-BE21-44DC-7720            │
│  [Copy]                         │
│                                 │
│  Send this code to get your     │
│  activation key                 │
│                                 │
│  Enter activation key:          │
│  [________________]             │
│  [Activate]                     │
└─────────────────────────────────┘
```

### Хранение

- Installation ID генерируется один раз и хранится в **таблице `config`** в БД (поле `installation_id`). Файл `~/.config/cc-manager/installation.json` не используется — единственный источник правды это БД.
- Токен после активации хранится в зашифрованной таблице `config` в БД
- При каждом старте приложения — `POST /verify` проверяет что токен активен
- Если сервер недоступен при старте — приложение запускается в **офлайн-режиме**: в сайдбаре показывается бейдж `⚠️ Offline — no sync`. Все локальные функции работают полностью. Footprints копятся локально и синхронизируются когда сервер снова доступен.

### Восстановление из бэкапа и лицензия

При восстановлении из `.ccbak` — токен лицензии в таблице `config` восстанавливается вместе с данными. Если бэкап был сделан на том же устройстве — всё работает. Если бэкап переносится на другое устройство — потребуется повторная активация (Installation ID будет другим).

**Footprints при restore:** восстанавливаются с тем же флагом `synced` что был в бэкапе. Записи с `synced: true` повторно на сервер не отправляются. Если какие-то попадут повторно — сервер дедуплицирует их по ключу `(shop_domain, hash_type, hash_value, user_token)`.

### Отзыв доступа

Администратор может заблокировать любого пользователя через админ панель одной кнопкой. При следующей проверке токена (`/verify`) приложение получит отказ и заблокируется.

| Поле | Описание |
|---|---|
| `installation_id` | Уникальный ID установки |
| `challenge` | Код показанный пользователю |
| `token` | Выданный токен активации |

## Автоблокировка

### Логика

Таймер неактивности отслеживается в Rust бэкенде. Сбрасывается при каждом `invoke()` с фронтенда. Фоновый поток проверяет каждые 30 секунд:

```rust
if last_activity.elapsed() > inactivity_timeout {
    db.clear_encryption(); // ключ шифрования стёрт из памяти
    emit_event("app_locked"); // фронтенд показывает экран блокировки
}
```

### Настройки в Settings — секция Security

```
Auto-lock timeout:
  [ 1 min ]  [ 5 min ]  [ 15 min ]  [ 30 min ]  [ Never ]
  ● 5 min (по умолчанию)

[ Lock Now ] — мгновенная блокировка
```

Таймаут сохраняется в таблице `config` в БД (не в localStorage).
